# v2.2.17 升级指南

## 先看这一条：从 2.2.16 升级需要手动重启一次

v2.2.17 修的正是「在线升级后服务起不来」。但执行本次关闭流程的是**旧版本**代码，所以从 2.2.16 用 WebUI 在线升级时，仍会卡在这一步。应用更新后请手动重启一次：

```bash
docker restart my-media-sub
```

重启后 `runtime/` 里的 2.2.17 载荷会被直接启动（在线升级的结果在容器重启后保留）。用下面这条确认版本：

```bash
curl -s http://127.0.0.1:56001/health
# {"status":"ok","version":"2.2.17"}
```

**2.2.17 之后的在线升级会自行完成重启，不再需要这一步。**

Docker Compose 部署也可以直接拉镜像，效果相同：

```bash
docker compose pull
docker compose up -d
```

v2.2.17 不修改 JSON Store schema，可直接复用 v2.2.16 的 `data/`。

## 本版本修了什么

### 在线升级后服务再也起不来

新版本二进制和 `static/` 都已正确落盘，`.installed-version` 也更新了，但进程停在「已停止监听、却不退出」的状态：

```
13:52:07  POST /api/update/apply    200
13:52:11  POST /api/update/restart  200
13:52:11  收到在线升级重启请求，开始优雅关闭
          ← 之后再无任何日志
```

HTTP 优雅关闭会等待所有在途连接结束，而 `/api/jobs/events` 是 SSE 长连接，永远不会自己结束——**点「更新」的那个页面自己持有的这条连接，就把这次升级永久卡死了**。因为进程始终没有退出，容器的 `unless-stopped` 重启策略也不会介入，表现为容器 `Up` 但健康检查一直失败、端口无人应答。

现在是双保险：

- 关闭开始时广播一次信号，SSE 流据此主动收尾，正常情况下秒级完成；
- 优雅关闭有 15 秒硬上限，任何赖着不走的连接（慢客户端、代理中的大文件）都不能再把重启卡住；
- `exec` 新版本失败时显式退出进程，交给 systemd / 容器重启策略拉起，绝不留下一个不再服务的存活进程。

新增端到端回归测试：开着 SSE 连接触发重启，优雅关闭必须完成——移除修复后该测试会超时失败。

### 开启「同步下载」的订阅永远不会转为已完结

这类订阅此前被完全排除在完结判定之外，完结与否只认下载监视器给 `sync_downloads` 记录打的 `completed_at`。而 Aria2 的任务历史是易失的（重启、`--max-download-result` 上限、手动清理都会丢），这个标记常年填不上；连一条下载记录都没有的订阅更是结构性地无法完结——线上实测 6 部片源已出齐、集数连续、全部转存完毕的剧集，其中 5 部的已完成下载记录数为 0。

现在它们与普通订阅一致，按转存证据完结，下载监视器的判定保留为额外触发路径。追更是否结束取决于片源是否出齐并已转存，本地镜像下载属于投递环节，不该成为完结的唯一凭据。

**升级后执行一次「批量检查」，符合条件的订阅就会移入「已完结」。** 如果某个订阅的判定结果不符合预期，订阅菜单里的「标记完结 / 重新追更」可以手动纠正（v2.2.16 新增），手动设置不会被自动推导覆盖。

## 二进制部署

手动升级时必须同时替换归档中的整个 `static/` 目录。前端资源 URL 带有 `?v=2.2.17`，Service Worker 缓存代次为 `v2.2.17-restart-and-completion-1`。

同样地，从 2.2.16 用 WebUI 在线升级时需要手动重启一次服务（`systemctl restart my-media-sub` 或等效命令）。
